Ambiten Core v1.3.0 — Modular Configuration and Runtime Defaults

External schema and model modules, declarative runtime defaults, tenant resolver integration, and more reliable application bootstrap behavior.

Written by Emmanuel Abiodun Nodolomwanyi
Product Update October 18, 2026 10 min read

Ambiten Core v1.3.0 improves the connection between application configuration and runtime behavior. Schemas and model options can live in external modules, JSON schemas can declare values that resolve during execution, and bootstrap configuration can connect directly to an external tenant configuration resolver.

The release also restores preparation of configured log files during startup, updates generated applications to request the current Core release, and addresses package compatibility across ESM, CommonJS, browser builds, and Windows build tooling.

v1.2.4 clarified how context, models, providers, and tenant infrastructure work together. v1.3.0 builds on those boundaries by making them easier to configure in an application.

Configuration identifies what an application needs. Modules organize its definitions. Execution context supplies the values that belong to the current operation.

Configuration That Can Grow With The Application

Inline configuration remains useful for a small application. A schema with a handful of fields and a model with a collection name can be easy to understand in one JSON file.

As the application grows, those definitions can occupy most of the configuration file. Reviewing a connection setting or tenant option then requires navigating through an increasingly large document.

In v1.3.0, the schema and model properties support external module references. Each reference identifies a file and the export that bootstrap should load.

For example, these properties can appear in ambiten.config.json: 

{
  "schema": {
    "path": "./src/schemas/user.schema.mjs",
    "exportName": "userSchema"
  },
  "model": {
    "path": "./src/models/user.model.mjs",
    "exportName": "userModelOptions"
  }
}

The schema module exports a schema definition object: 

// src/schemas/user.schema.mjs

export const userSchema = {
  tenantId: {
    type: "string",
    required: true,
    default: {
      $runtime: "context",
      key: "tenantId"
    }
  },

  publicId: {
    type: "string",
    default: {
      $runtime: "uuid"
    }
  },

  username: {
    type: "string",
    required: true
  },

  email: {
    type: "string",
    required: true
  },

  createdAt: {
    type: "date",
    required: true,
    default: {
      $runtime: "now"
    }
  },

  isDeleted: {
    type: "boolean",
    default: false
  },

  deletedAt: {
    type: "date"
  }
};

The model module exports model options: 

// src/models/user.model.mjs

export const userModelOptions = {
  collectionName: "users"
};

Bootstrap loads these objects and constructs the schema and model infrastructure. Inline definitions remain supported, so each application can choose the organization that fits its size.

Paths in a JSON configuration file resolve relative to that file. Paths in a programmatically supplied configuration object resolve relative to the process working directory. Omitting exportName selects the default export.

The existing features.schemas and features.models values describe scaffolding locations. Runtime module loading is configured through the schema and model properties; it does not scan those feature directories automatically.

Runtime Defaults Resolved Per Document

Some document values only make sense when an operation runs. A creation timestamp belongs to the document being created. A generated identifier should be produced for that document. A tenant identifier depends on the active execution.

v1.3.0 introduces declarative $runtime defaults that express these requirements in a JSON-compatible schema.

  • { "$runtime": "now" } creates a Date when the default is applied.
  • { "$runtime": "uuid" } generates a UUID.
  • { "$runtime": "context", "key": "tenantId" } reads the tenant identifier from the active AmbitenContext.

Context defaults support tenantId, requestId, dbName, and collectionName.

Using the schema above, validation can resolve the missing values within an execution context: 

import {
  AmbitenContext,
  Schema
} from "@ambiten/core";

import {
  userSchema
} from "./schemas/user.schema.mjs";

const schema = Schema.create(userSchema);

const document = {
  username: "Alice",
  email: "alice@example.com"
};

await AmbitenContext.run(
  { tenantId: "tenant-a" },
  async () => {
    await schema.validateAsync(document);
  }
);

This example performs schema validation without a database write. Validation adds the tenant identifier, a UUID, a creation timestamp, and the isDeleted default to the document.

Defaults apply when a field is undefined. Supplied values remain subject to validation. Object and array defaults are copied for each document, preventing separate documents from sharing the same mutable default value.

Unsupported runtime directives and context keys are rejected. A context default also fails when its requested value is unavailable during execution.

The same default contract applies to inline schemas and external schema modules: use JSON-compatible literal values or supported $runtime descriptors.

Creation And Deletion Have Different Defaults

The example deliberately leaves deletedAt optional and without a default.

A newly created document has isDeleted: false and no deletion timestamp. A deletion workflow can assign a date when deletion occurs.

A date field requires a valid Date value when supplied. Assigning false to deletedAt violates that type, while defaulting it to the current time incorrectly records a deletion timestamp at creation.

External Tenant Configuration Through Bootstrap

Ambiten already separates tenant identity from tenant infrastructure. A request resolver identifies the tenant, AmbitenContext carries that identity, and MultiTenantManager resolves the corresponding database resources.

v1.3.0 extends the JSON configuration path with multiTenant.tenantConfigResolverModule. Applications can now connect an external tenant configuration resolver through the same file-and-export pattern. 

{
  "multiTenant": {
    "enabled": true,
    "tenants": {},
    "tenantConfigResolverModule": {
      "path": "./src/tenantResolver.mjs",
      "exportName": "resolveTenantConfig"
    },
    "initOptions": {
      "lazy": true
    }
  }
}

The selected export is a function receiving a tenant identifier. It returns tenant configuration, or undefined or null when the tenant cannot be resolved.

A small application might resolve an explicit set of tenant identifiers from environment-provided connection strings: 

// src/tenantResolver.mjs

const tenantUris = new Map([
  ["tenant-a", process.env.TENANT_A_MONGODB_URI],
  ["tenant-b", process.env.TENANT_B_MONGODB_URI]
]);

export function resolveTenantConfig(tenantId) {
  const uri = tenantUris.get(tenantId);

  if (!uri) {
    return undefined;
  }

  return { uri };
}

The function can also be asynchronous when configuration comes from a control database, account service, configuration API, or another application-owned source.

Resolved configuration contains a MongoDB uri, with optional dbName and metadata. MultiTenantManager manages registration and client state.

Static tenants and dynamically discovered tenants can coexist. The local registry is checked first; the external resolver supplies configuration for tenants that are not registered.

Request authentication and authorization remain application responsibilities. Resolving a tenant's database configuration does not establish whether a caller may access that tenant.

Log Files Prepared During Startup

Bootstrap logging should make its configured destination available when the application initializes.

v1.3.0 restores preparation of the parent directory and log file for declaratively configured file transports. Bootstrap resolves the destination, creates missing directories, and opens the file in append mode before constructing the transport.

An explicit console and rotating-file configuration can look like this: 

{
  "logger": {
    "enabled": true,
    "level": "info",
    "transportConfigs": [
      {
        "type": "console",
        "options": {}
      },
      {
        "type": "rotating-file",
        "options": {
          "filename": "./logs/ambiten.log"
        }
      }
    ]
  }
}

Relative log destinations resolve from the process working directory. Existing file contents are preserved, and a failure to prepare the destination is reported during initialization.

When logging is enabled and no transports are supplied, bootstrap uses its default console and rotating-file transports. An explicit console-only runtime configuration remains console-only.

Applications supplying their own logger instance or executable transports retain responsibility for configuring those transports.

Module Loading Follows The Application Runtime

External configuration modules use native module loading, with support for selecting exports from ESM and CommonJS modules. File paths are converted to file URLs so Windows paths can participate in the same loading process.

The examples in this article use .mjs files so their module format is explicit.

Applications using .ts configuration modules need TypeScript support in the process performing the native import. With tsx installed, a development command can be: 

node --import tsx src/main.ts

A CommonJS require hook alone does not provide that native import support.

For compiled deployments, point configuration references at the emitted JavaScript files and include those files in the deployment. Compiling the application does not automatically rewrite module paths inside its JSON configuration.

Stronger Package Boundaries

Runtime behavior also depends on how packages are built, installed, and imported.

This release includes corrections to emitted ESM references, package-boundary compatibility, browser bundle compilation, and Windows package-manager invocation.

  • ESM module references include the file extensions required by Node.js.
  • Package integration checks cover CommonJS and ESM consumption across Core, adapter types, adapter runtime, and the Express adapter.
  • Those checks also cover the request context used across the tested Core and adapter package boundaries.
  • Browser build errors involving Node.js module imports have been addressed.
  • Build and package integration scripts handle Windows invocation of pnpm more reliably.

These changes support the runtime architecture described in the previous release: an adapter establishes execution context, and application operations must be able to observe that same context through the installed packages.

Related packages retain their own version numbers. v1.3.0 identifies this Core release.

Bootstrapping With The Current Core Release

Generated applications now declare: 

{
  "dependencies": {
    "@ambiten/core": "latest"
  }
}

During the initial dependency installation, the package manager resolves the version published under the registry's latest tag.

This makes the scaffold's intent explicit and allows a newly generated application to begin with the current tagged Core release, including when that tag moves beyond the original major-version range.

The installed dependency tree and lockfile then record the selected version. Existing applications continue to control dependency updates through their normal package-management workflow.

Interactive scaffold summaries have also been updated to accommodate the revised model configuration structure.

Installing Ambiten Core v1.3.0

Install or update Core with: 

pnpm add @ambiten/core@1.3.0

Or with npm:

npm install @ambiten/core@1.3.0

To run the bootstrap CLI supplied by this release: 

pnpm --package=@ambiten/core@1.3.0 dlx ambiten init my-app

This command selects the v1.3.0 CLI. The generated application's Core dependency still uses latest, which is resolved when its dependencies are installed.

Review The Generated MongoDB Dependency

There is a dependency mismatch to account for in the v1.3.0 scaffold: its generated MongoDB range is ^6.14.2, while the published Core package declares ^5 || ^7 as its MongoDB peer range. Align the application's driver version with Core's declared compatibility and the selected driver's Node.js requirements.

Review Configuration During An Upgrade

  • Existing inline schema and model definitions can remain inline.
  • External module references must point to files available to the running application.
  • Schema defaults should use supported literal values or $runtime descriptors.
  • A context default requires its requested value to be available when validation applies the default.
  • File logging requires a file transport in an explicitly supplied transport list.
  • Adapter dependencies should be reviewed alongside Core, using each package's own release version.

Documentation Following The Runtime

Documentation work accompanying v1.3.0 covers schema definitions, runtime defaults, multi-tenancy, external configuration modules, AmbitenBootstrapFactory, CLI scaffolding, and advanced usage.

The examples distinguish the configuration loaded during startup from the state established for an individual request, operation, or background job.

They also clarify how applications establish transaction boundaries, carry tenant identity into worker execution, configure logging, and coordinate resource shutdown.

These distinctions help developers connect a working example to the responsibilities of a larger application.

From Configuration To Execution

An application can begin with a small inline schema, move its definitions into modules as they grow, and connect an external tenant configuration source through bootstrap. Runtime defaults then supply document values from the execution in which those documents are validated.

Ambiten Core v1.3.0 makes those choices easier to express while preserving the separation between reusable infrastructure and execution-specific state.
